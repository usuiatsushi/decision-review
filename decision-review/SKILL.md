# Decision Review v0.1

目的は人間のレビュー対象を重要な意思決定に絞ること。実験中は成果物の差分確認、テスト、最終Acceptanceも行う。

## 手順

1. Intent、成功条件、制約、既存合意、現行Spec・Design、今回の差分、AIの提案と検証結果を確認する。未提供のものは明記する。初回生成では新たに置く仮定と仕様上の選択を差分とする。明示事項とAIの推測を区別する。
2. 採用した選択、退けた主な代替案、未確定の仮定を候補として洗い出す。要件・設計・実装の境界で新たに生まれた選択も確認する。
3. 各候補にE1〜E6を適用する。いずれかに該当したら人間に上げ、該当IDと具体的な影響を記す。迷えば上げる。
4. 非掲載候補の種類と省略理由を後から説明できるよう短く記録する。全候補の提出は不要。票の件数を減らすために該当候補を隠さない。
5. 票を提示し、人間の承認・修正・質問・保留を受ける。回答の矛盾、見落とした影響、実現上の問題をAIが再レビューする。異論には理由と代替案を添えて再判断を求め、判断を黙って上書きしない。
6. 確定した判断をSpecまたはDesignの該当箇所に反映し、実装・テストとの対応を確認する。保留に依存する確定・不可逆な作業は進めず、独立した作業は続ける。

## エスカレーション条件

「決定」は複数の妥当な選択肢があり、採用案が成果物や利用者の振る舞いに影響する選択を指す。

| ID | 人間に上げる条件 |
| --- | --- |
| E1 | 目的・成功条件・対象ユーザーの解釈が分かれ、既存合意から選べない。 |
| E2 | 外部から見える振る舞い、業務手順、入力・出力、権限、データの保持・削除を変える。 |
| E3 | セキュリティ、プライバシー、安全性、法令・契約上の義務、金銭、重大な障害に影響しうる。現実的な影響経路を説明できる可能性も含む。 |
| E4 | 後から変更しにくい、移行・他システムとの調整が必要、または波及範囲が広い。 |
| E5 | Intent・制約・既存Specと矛盾する、または解消に優先順位の判断が要る。 |
| E6 | 重要な情報がなく、仮定が外れればE1〜E5の影響が出る。 |

既存Specが一意に定める実装、内部だけで容易に戻せる選択、動作に影響しない命名・整形は通常上げない。ただしE1〜E6に該当すれば上げる。既承認でも前提が変われば再度上げる。件数が多ければ変更単位を分ける。

## 出力

冒頭に対象段階（要件／設計／実装）、差分、参照資料、未提供資料、結論（要判断あり／なし）を記す。独立した論点は分け、同じ人間判断で解決するものはまとめる。各Decisionに以下を含める。

| 項目 | 記載内容 |
| --- | --- |
| ID・論点 | 人間が何を選ぶか。 |
| 上げた理由 | E1〜E6と具体的な影響、関連する仮定。 |
| AI推奨・根拠 | 推奨案とIntent・Spec・検証結果の該当箇所。推測は明示。 |
| 代替案・違い | 主要な代替案と選択時の違い。実質的な代替案がなければ理由。 |
| 影響範囲 | 利用者、データ、API、設計、実装、テスト等。 |
| 人間判断 | 承認／修正／質問／保留を記入できる欄。 |

複数の判断に依存関係があれば順序を示す。ゼロ件でも「要判断なし」と確認範囲、省略した候補の主な理由、残る不確実性を示す。根拠不足なら必要な確認を示す。

## 実験で改善する

小規模な変更1件で、まず票だけを人間が判断し、その後に差分を確認する。票を読む時間、差分確認時間、不要な掲載、差分で見つかった未掲載の重要判断、根拠不足を記録する。見落としには該当E条件と漏れた理由を付け、基準を修正する。時間短縮より見落としの改善を優先する。
